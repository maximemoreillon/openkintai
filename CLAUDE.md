# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OpenKintai is a minimal clock-in/clock-out (attendance) tracker built on Nuxt 4 + NuxtHub + Vuetify, with Postgres/Drizzle for storage and OIDC for auth.

**Design principle: stay minimal.** This app deliberately has no internal user management and no internal auth system — identity and authentication are fully delegated to the OIDC provider. `isManager` is a group check performed at login, not a role system — it grants the ability to view other users' shifts and edit any shift's notes (but not clock-in/out times, which stay deferred — see the shift-editing note below). Don't add user CRUD, invite/signup flows, password auth, permission management UI, or similar — if it's not already here, it's out of scope unless the user asks for it.

## Commands

- `npm run dev` — start the dev server at `http://localhost:3000`
- `npm run build` — production build
- `npm run generate` — static generation
- `npm run preview` — preview a production build
- `npx nuxt db generate` — generate a new migration after editing `server/db/schema.ts` (NuxtHub's own CLI command; it runs `nuxt prepare`, rebuilds the schema, then calls `drizzle-kit generate` under the hood). Generated migrations go in `server/db/migrations/postgresql/`. NuxtHub auto-applies pending migrations on `npm run dev` start, but `hub.db.applyMigrationsDuringBuild` is explicitly set to `false` in `nuxt.config.ts` — apply migrations in production with `npx nuxt db migrate` as its own deploy step.
- **`hub.db.driver` is explicitly set to `postgres-js`** in `nuxt.config.ts` — without it, NuxtHub resolves the driver from `DATABASE_URL` once, at build time, and silently falls back to an embedded `pglite` database if it's absent then (as it always is in `docker build`, which intentionally never sees `DATABASE_URL`). Worse, when `DATABASE_URL` *is* present at build time, NuxtHub bakes the literal connection string into the compiled server bundle rather than reading it at runtime — so `docker build --build-arg`/`--secret` for this is a trap, not a fix, since the credential still ends up inside `.output/` either way. Forcing the driver sidesteps both problems: NuxtHub's production `postgres-js` codegen path reads `process.env.DATABASE_URL` live at server startup whenever the connection URL wasn't already known at build time. `DATABASE_URL` should only ever be set where the container/process actually runs, never passed to `docker build`.

There is no lint or test setup in this repo currently.

## Architecture

- **Nuxt 4 app directory layout**: pages/components/middleware/plugins live under `app/`, not the repo root.
- **NuxtHub (`@nuxthub/core`) owns the database wiring.** `hub.db` in `nuxt.config.ts`, combined with `server/db/schema.ts`, causes NuxtHub to generate the `@nuxthub/db` module. This exposes two server-side auto-imported globals used throughout `server/api/**` and `server/utils/**`: `db` (a Drizzle client) and `schema` (the Drizzle schema from `server/db/schema.ts`). Neither is imported explicitly in route handlers — they're ambient globals, resolved via `.nuxt/types/nitro-imports.d.ts`. Do not add manual imports for them.
- **Two-table schema** (`server/db/schema.ts`): `users` (keyed by `(issuer, sub)` from OIDC, plus `isManager`) and `shifts` (`user_id`, `clockIn`, nullable `clockOut`). An open shift is one where `clockOut` is null.
- **Auth flow**:
  - `server/routes/auth/oidc.get.ts` handles the OIDC callback (`nuxt-auth-utils`'s `defineOAuthOidcEventHandler`), decodes the ID token to get the issuer, and calls `upsertUser` (`server/utils/users.ts`) to create/update the local user row and set the session.
  - The OIDC redirect URI defaults to being inferred from the request (trusting `X-Forwarded-Proto`), which breaks behind proxies/tunnels that don't set that header correctly (observed with Cloudflare Tunnel — the app told Authentik its callback was `http://` while actually served over `https://`). `runtimeConfig.oauth.oidc.redirectURL` (`NUXT_OAUTH_OIDC_REDIRECT_URL`) overrides it explicitly; leave unset unless a deployment needs it.
  - `isManager` is derived purely from OIDC `groups` matching `runtimeConfig.managerGroup` (`NUXT_MANAGER_GROUP` env var) at login/upsert time — it is not editable elsewhere.
  - `server/middleware/auth.ts` requires a session for every `/api/*` request (`requireUserSession`).
  - `app/middleware/auth.global.ts` is a Nuxt global route middleware that redirects unauthenticated users to `/login` for every page except `/login` and `/auth/*`.
  - Session `User` shape is declared in `shared/types/auth.d.ts` (augments `#auth-utils`).
- **API routes** (`server/api/**`) are thin: read the session user, run one Drizzle query/mutation against `db`/`schema`, return the result. The self-only `shifts` endpoints (clock in/out, active-shift check) scope to `user.id` from the session; `shifts/[id]` (`GET`/`PATCH`, a single shift's notes) scopes its query to the shift's owner or an `isManager` user. `users/[id]/shifts` and `users` do not check `isManager` server-side at all — every user (not just managers) is linked to their own `/users/{id}/shifts` from `/`, and the `Users` list nav link (`app/pages/index.vue`) is only hidden client-side via `user?.isManager`. This is consistent with the minimal-auth design above (any authenticated OIDC user can reach these routes); don't "fix" it by adding a role/permission layer unless asked.
- **Frontend**: Vuetify (`app/plugins/vuetify.ts`, dark theme by default) for all UI. `/` (`app/pages/index.vue`) is just the clock-in/out buttons plus a "My shifts" link to the current user's own `/users/{id}/shifts`, and (for managers) a "Users" link to `/users`. `/users` lists users (nav link hidden for non-managers, not server-enforced); `/users/[id]/shifts` is the shared shift-history page, used both by a manager viewing someone else and by any user viewing their own — mirroring the `users`/`users/[id]/shifts` API routes. A shift's notes are edited on `/users/[id]/shifts/[shiftId]` (linked from the pencil icon in `ShiftsTable`), which navigates back up via its own reconstructed breadcrumbs (Home / Users / user name / Shifts / shift) rather than `router.back()`. `app/utils/dateUtils.ts` has shared formatting helpers (`formatTimestamp`, `timeBetweenTimeStamps`) used by the shift tables.
- **Config**: `nuxt.config.ts` declares `runtimeConfig.managerGroup`, `runtimeConfig.oauth.oidc.{clientId,clientSecret,openidConfig}`, and `runtimeConfig.public.{locale,userManagementUrl,breakRules}` (`locale` used by `formatTimestamp` in `app/utils/dateUtils.ts`; `userManagementUrl` is an optional external link — e.g. to the OIDC provider's user admin screen — shown as a button on `/users` when set; `breakRules` is a comma-separated `hoursThreshold:breakMinutes` list, e.g. `6:30,8:60`, parsed by `app/utils/breakRules.ts` and deducted from the worked-hours total shown/exported on `/users/{id}/shifts` — empty means no deduction, since break policy is business-specific, not something OpenKintai prescribes), populated via env vars in `.env` (`NUXT_MANAGER_GROUP`, `NUXT_OAUTH_OIDC_*`, `NUXT_PUBLIC_LOCALE`, `NUXT_PUBLIC_USER_MANAGEMENT_URL`, `NUXT_PUBLIC_BREAK_RULES`, plus `DATABASE_URL` and `NUXT_SESSION_PASSWORD`).
- **Timezone**: `shifts.clockIn`/`clockOut` are plain `timestamp` columns (no timezone). `server/api/users/[id]/shifts/index.get.ts` takes `from`/`to` query params and parses them with `shared/utils/dateRange.ts`'s `parseLocalDate`, which builds a `Date` from `(year, month, day)` components — interpreted in the server process's local timezone, not UTC (unlike `new Date(dateString)` on a bare date string). This only produces correct attribution if the deployment's `TZ` env var matches the business's real timezone — set `TZ` (e.g. `TZ=Asia/Tokyo`) wherever the app is deployed. This is a deliberate operational fix rather than a code-level one (storing `timestamptz` + an explicit configured zone), consistent with this app's one-deployment-per-business assumption.
